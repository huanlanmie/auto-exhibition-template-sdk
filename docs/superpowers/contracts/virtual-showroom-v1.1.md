# Virtual showroom software interaction contract v1.1

Supersedes v1's local-only/single-runtime restriction. Existing scene schemaVersion 1 and MessagePort protocolVersion 1 remain valid. User approved visitor-local software interaction and requested implementation plus local frontend/backend startup. No automated functional tests or browser QA; builds and minimal service readiness checks are allowed.

## Scene graph and management

Optional `sceneDocument.interactionGraph = {schemaVersion:1,rules:[],groups:[],quizRooms:[]}`. Missing means an empty graph. SaveDraft may edit this graph, but server must validate it against authorized bound instance function manifests. Separate PUT graph also accepts `{expectedDraftVersion,interactionGraph}` and uses ordinary owner/CAS, never writes physical function_binding_rule or publishConfig.

Rule: `{ruleId,name?,enabled:true,sourceScreenId,sourceFunction,targets:[{endpointType:'template',screenId,functionName,argsMapping?}|{endpointType:'quiz',roomId,functionName}],ttl:8}`. IDs are [A-Za-z0-9_-] bounded strings. Maximum 128 rules, 16 targets/rule, 8 active runtimes/visitor. Function source direction out/both, template target in/both. Arguments mapping is a JSON object whose values may be constants or exact `$args.path` / `$context.from.clientId` paths; no eval, prototype paths or expressions. An empty mapping forwards args. Quiz functions: joinQuizRoom/joinQuizRound/startQuestion/buzz/submitAnswer/resetQuestion/nextQuestion/endQuiz/syncQuizState; quizArbiter from old physical rules is expanded to the known source function.

Group: `{groupId,name?,screenIds:[...]}`. Quiz room: `{roomId,name?,screenIds:[...],masterScreenId?,waitSeconds:30,countdownSeconds:10}`; members must use bound quiz-buzzer templates; private source room/client IDs cannot appear publicly. Templates and quiz room membership reference enabled, bound, interactive screens. Max 8 interactive screens participating in one graph; unrelated preview-only screens are allowed.

Admin endpoints relative `/virtual/admin/showrooms/{id}`:
- GET `/interaction-catalog` → data `{screens:[{screenId,name,templateInstanceId,instanceVersion,templateCode,functions:[{name,direction,label?,params?}]}],sourceRules:[],contentVersions:[]}`. Source rules only owner-authorized, mapped unambiguously to screens; unsupported/ambiguous physical targets return diagnostics, never executable public targets.
- PUT `/interactions` body above → updated showroom detail.
Existing template instance picker adds `deviceName,deviceCode,deviceId,themeName,themeId,sourceConfigId,templateCode` for admin use. Content version data distinguishes source, draft and public revision; actual field deployment is `unknown` until a receipt exists. No physical receipt changes in this stage.

Published graph is immutable with scene. Public manifest adds `runtimeCapabilities:{virtualRouting:true,maxRuntimes:8}` and `screenFunctions` (keyed by screenId with actual manifest functions and templateCode). Both are derived server-side from the fixed resource/config snapshot, not current cloud instances. Existing revisions without graph receive empty graph but authorized catalog as available. Public snapshots contain no physical source clientId/deviceId/endpoint/hardware/gateway destinations. Validation blocks invalid graph/function/source/target ownership and newly stale bindings; absent source emits actionable source status.

For staged content updates, draft writes may retain a stale binding only when the previous draft contains the same enabled interactive screen with an exactly equal contentBinding. Ownership, template authorization, sourceConfig consistency and graph/function/resource validation still apply. New, re-enabled or changed bindings require freshness. Publication always checks all enabled interactive bindings without this draft exception. This allows several screens to be refreshed individually while retaining their interaction graph.

## SDK and runtime transport

Injected BrowserHostConfig optional `capabilities:{virtualRouting:true}`. Default absent is legacy local-only. Exact origin/source/identity and window ACK followed by port sdk_ready remain unchanged. Outbound virtual-capable transports accept local/binding/unicast/multicast/broadcast target shapes; unknown target rejects explicitly. Local templateSessionId must match own runtimeId. Inbound host-delivered template_function_call must still be rewritten to local receiving runtime target and verified by SDK. Host is authoritative; SDK never opens physical WS/fetch. sdk_ready.clientId is `v:<visitorSessionId>:<screenId>` stable for the visitor/screen; runtimeId changes per frame load.

createHostSession options add `virtualClientId,onMessage`; returns `{identity,send,dispose,updateValueMap}`; no global active session. Each authenticates its own frame/port. hostSession delegates business routing to room runtime. Old standalone preview may be implemented through a one-screen room, not a global singleton.

Authenticated port control `host_visibility` carries a strict boolean `visible`. Hidden native and legacy frames pause current audio/video and capture later play events; visibility restoration does not automatically play media. Dispose removes the capture listener. Window messages cannot invoke this control.

`createVirtualRoomRuntime({manifest,resolveAsset,mountTarget,onError,maxRuntimes?})` returns `openScreen(screenId):Promise`, `closeScreen()`, `dispose()`, `getScreenStatus(screenId)`, `onState(handler)`. It owns lazy runtime frames, ports, registrations and pending calls. Front display contains one visible proportional iframe, other participating frames are bounded and hidden; closing preserves their visitor-local state, leaving/reloading room destroys all. maxRuntimes cannot exceed manifest cap. Target readiness is awaited with timeout; oversized graph fails clearly rather than silent eviction losing state. Media in hidden frames is suspended where possible; no physical requests.

Router: local only sender; binding only enabled frozen source/function rules; unicast only exact virtualClientId; multicast only explicit virtual IDs or frozen group; broadcast only this room. Intersect frozen incoming function allowlist and runtime register_functions. Overwrite `from` with logical sender clientId. Fan-out with expectResult returns first successful result, or error after all fail; child deliveries use unique message IDs mapped to original sender request. TTL decreases, bounded recent trace prevents loops. Hardware/physical unknown IDs never route. Events similarly remain room-scoped. Storage remains triple-identity scoped. No cross-visitor state.

Quiz adapter operates only declared room members, derives sender from trusted identity, bounds timers/data, returns request results and sends local function calls syncQuizState/memberJoined/buzzResult/answerResult/quizRoundInvite/quizRoundReady/resetQuestion. Enforce one winner per question, server-in-browser clock deadlines, master-only control, answer from winning/solo participant, and reject forged member IDs. State fields must match the actual quiz-buzzer template. First participant may become master if none declared, but never use physical room IDs or share visitors.

## Execution and startup

Preserve current branches/checkouts and user edits; root alone commits. Backend owns virtual Java; SDK owns SDK source; frontend owns virtual UI except root Vite startup proxy edit. Separate startup overrides instead of editing existing bootstrap/Nacos. Disable local Nacos service registration; use explicit local gateway routes. Never stop unrelated processes or issue field-control commands. Existing configured remote dependencies may be read for configuration/readiness; schema writes require confirming target is local/development and preserving existing data, never destructive reset. Local secrets stay ignored and are not printed. Background helpers launch hidden. Actual ports/logs/PIDs recorded in local startup handoff.
